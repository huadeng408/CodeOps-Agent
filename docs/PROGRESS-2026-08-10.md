### 6.3 编码 bug：实测发现并修复（`VERIFIED`）

首次 E2E 时模型主动报告 hook 反馈是乱码。实测定因，不是猜：


`utf-8` 解码在 position 33 的 `0xc9` 失败，`gbk` 解码完好 → **hook 吐的是 GBK 字节**，

修后：`...2022 e4b88a e4b880 ...` —— `utf-8` 解码 OK、`gbk` 反而在 position 65 的
`0xaa` 失败，`reason` 字段完整可读。

## 12. Hook 的覆盖边界：API 错误路径不走 Stop hook（`VERIFIED`）

在 `d:\vscode\a-issues-and-misc` 的一个窗口上实测得到一条重要的**能力边界**：
`continue-guard.py` 治不了被 API 错误打断的回合。

现场：会话 4.8MB / 1441 行，连续三次停在一句叙述后，用户三次打「继续吧」。
形似 promise-stop，实则不是：

| 行 | `stop_reason` | `output_tokens` | 判定 |
|---|---|---|---|
| r1423 / r1429 / r1439 | **`None`** | 1 | 响应刚开头即被掐断的残片 |
| 正常结束回合 | `end_turn` | 正常 | — |

该窗口 `Stop-hook injections = 0`，印证 **Stop hook 只在回合正常结束时触发**，
被 API 错误打断的路径根本不经过它。

根因是**冷 prompt cache 超时**，`usage` 字段为决定性证据：

```text
r1422  cache_read=106033  cache_creation=667     缓存命中 → 正常
r1429  cache_read=0       cache_creation=118845  全量重建
r1439  cache_read=0       cache_creation=125822  全量重建
```

`input_tokens=0` 配 `cache_creation_input_tokens=118845`，即整个 12 万 token 前缀
从零重写缓存。用户两次重试间隔 14 分钟与 12 分钟，均超过 prompt cache 的 5 分钟 TTL。

超时常数精确到可疑：`03:48:57→03:52:57`、`04:06:37→04:10:38`、`04:18:52→04:22:53`，
三次均为 4 分 00/01 秒 → **网关超时被报成 403 `Upstream access forbidden`**，
非鉴权失败（鉴权是毫秒级返回）。

体积不是判别量：403 出现在 88k/88k/156k/117k/118k/125k，而 88k 在会话前期成功过
（当时缓存是热的）。

**与本轮配置改动无关，用证据排除**：该窗口 460 次请求的 model 全为 `claude-opus-5`，
`[1m]` 从未出现；`[1m]` 是 08-10 01:53 才进 settings.json 的，而该窗口 08-09 17:19 启动。
**env 在进程启动时读取，今天的编辑到不了已运行的窗口。** 代理同理：
`bak-router @08-09 16:42` 已含 `127.0.0.1:7890`，早于窗口启动 37 分钟。

处置：不在原窗口反复重试（只会重复同一个 4 分钟循环），改为开新窗口、以小前缀重述任务。

### 12.1 由此明确的 hook 能力边界

`continue-guard.py` 覆盖「模型自己把叙述当成回合结束」；**不覆盖**
API 错误、网关超时、以及任何 `stop_reason=None` 的截断残片。
§8 的 74%/20% 是对 promise-stop 的度量，**不是对全部早停现象的度量**。

## A.2 Defect J 真因（`VERIFIED`，且推翻我此前的判断）

我先前记为「构建容器没网」。**这是错的**，用日志证伪：克隆真的连上 github 并流了约 10 分钟才死。

```
+ git clone -o origin --single-branch https://github.com/astropy/astropy /testbed
Cloning into '/testbed'...
error: RPC failed; curl 92 HTTP/2 stream 0 was not closed cleanly: CANCEL (err 8)
fatal: fetch-pack: invalid index-pack output
The command '/bin/sh -c /bin/bash /root/setup_repo.sh' returned a non-zero code: 128
```

真因在**我们自己的代码**：`_run_official_scoring_local()` 与 `_run_official_scoring_wsl()`
两处都硬写 `namespace=None`，覆盖了 `swebench.harness.run_evaluation` 自己的默认值
`namespace="swebench"`。`None` 的语义是「本地构建每个实例镜像」，而本地构建必须执行
`setup_repo.sh`，也就是**在构建容器内克隆项目全history**。astropy 的全量克隆在本机网络下
不可靠，于是官方评分在第一个真正到达它的实例上必然失败。

实测确认（每项都有控制组，不是推断）：

| 事实 | 证据 |
| --- | --- |
| 预构建镜像上游存在 | `docker pull` 输出 `Pulling from swebench/sweb.eval.x86_64.astropy_1776_astropy-12907`；镜像已落地 3.92GB |
| daemon pull 路径可用 | 控制组 `docker pull hello-world` 成功 |
| `docker manifest inspect` 失败**不能**证明镜像不存在 | 控制组 `docker manifest inspect alpine:latest` 同样失败 → 它是**客户端侧**操作，WSL 无代理；`docker pull` 走 daemon（daemon 已配 `http.docker.internal:3128`） |
| namespace 非空时不会静默回落到失败的构建 | `docker_build.py`：`images.get` → `images.pull` → 失败即 `BuildImageError` |

修复：`_resolve_namespace()` 读 `SWEBENCH_NAMESPACE`，默认取上游值；`none` / 空值恢复本地构建
（离线主机用）。哨兵 `_UNSET` 使显式 `namespace=None` 与「调用方没传」可区分。15 tests。

**我另外证伪的一条自己的推断**：`/dev/tcp` 探针报 `http.docker.internal:3128` 不可达 ——
busybox `ash` 不实现 `/dev/tcp`，那些 `DEAD` 行是探针假象。只有 `curl` 结果与
「Clash 仅绑 `127.0.0.1`」（PowerShell 实测）可采信。

## A.3 `--dry-run` 什么都没校验（`VERIFIED`，本轮新发现）

dry-run 分支在 H0/H3 pin preflight **之前**返回，打印
`dry-run OK: manifest validated`，对 pin 完全缺失的 benchmark 也以 0 退出。
那条路径上既没构建 manifest，也没读任何 pin。

**一个不可能失败的 preflight 不是 preflight** —— 而且这里它主动误报：人们用来确认
「我配好了吗」的唯一命令，恰恰是检测不出配错的那条命令。

修复：pin 校验前移，dry-run 受其门禁。6 tests，其中一条驱动**真实** adapter 而非 stub。

## A.4 编码故障伪装成评分结果（`VERIFIED`，本轮新发现）

官方 scorer 的 WSL 调用用裸 `text=True`，stdout 按 locale 编码解码（本机 zh-CN = gbk）。
reader thread 抛 `UnicodeDecodeError: 'gbk' codec can't decode byte 0x93 in position 3912`，
线程死掉，`communicate()` 返回残缺缓冲，调用方**收不到任何异常**。

落到产物里的证据长这样：

```
scorer_status = 'official: resolved=False (WSL2 official scoring completed: : 0
Instances unresolved: 0 ...'
```

`Instances resolved` 这个标签被吃掉了，只剩 `: 0`。**一个编码故障把自己伪装成了评分结论。**

我此前把它归给 `_capture_git_diff`，**这是错的**：position 3912 远超 506 字节补丁，
且 602 行的克隆调用用 bytes 模式（无 `text=True`），不可能抛这个异常。真正的现场是
scorer 调用本身。

修复：所有 text-mode subprocess 调用钉死 `encoding="utf-8", errors="replace"`；
用 AST 测试守住整个缺陷类（新增未钉死的调用会被抓），外加行为测试证明
traceback 里那个真实字节 `0x93` 现在能安全通过。4 tests。

## A.5 官方原始输出从来不是发布证据（`IMPLEMENTED`，未经真实 run 验证）

H5 要求「保存官方 raw output」，§20.7 规定它落 `scorer/`。**生产代码从不写这个子树** ——
